# backend_go — шаблон Go API-бэкенда

Базовый шаблон Go-бэкенда для создания API-сервисов на базе Gin, GORM и PostgreSQL (или другой БД совместимой с GORM). Предназначен как отправная точка при разработке новых проектов: содержит готовую инфраструктуру для конфигурации, подключения к базе данных, миграций, типобезопасных CRUD-операций через дженерик-репозитории, планировщика задач, middleware, логирования, обработки ошибок и API-документации.

## Технологический стек

- Go 1.27.1
- Gin — HTTP-фреймворк
- GORM — ORM для PostgreSQL (драйвер pgx)
- Viper + godotenv — конфигурация с поддержкой YAML и .env файлов, переменных окружения и дефолтных значений
- gocron — планировщик задач
- gormigrate — миграции схемы БД
- zerolog + lumberjack — структурированное логирование с ротацией файлов
- swaggo/swag — генерация OpenAPI-спецификации из аннотаций в коде
- Scalar — интерактивная API-документация (доступна в debug-режиме)
- go-playground/validator — валидация входных данных
- morkid/paginate — пагинация с поддержкой фильтрации и сортировки

## Архитектура

### DI-контейнер

Приложение использует паттерн ручного dependency injection через центральный контейнер (app_container.Container). Инициализация происходит в строгом порядке: репозитории → сервисы → хендлеры → middleware → планировщик. Каждый слой получает зависимости из предыдущего. Контейнер также хранит конфиг, логгер и атомарный флаг готовности IsReady.

### Флаг готовности IsReady

Атомарный флаг (*atomic.Bool) управляет доступностью приложения. При старте он устанавливается в false и переключается в true только после успешного применения миграций и инициализации планировщика. Middleware IsReadyMiddleware блокирует все запросы, пока приложение не готово, возвращая страницу «не готов». Единственное исключение — эндпоинт /api/v1/status/logs в debug-режиме. Бэкап-задача также временно сбрасывает флаг в false на время выполнения, останавливая обработку запросов.

### Жизненный цикл приложения

1. main вызывает GetContainer, который инициализирует все слои зависимостей.
2. IsReady устанавливается в false.
3. В горутине запускаются миграции (с rollback при ошибке) и, если включено — планировщик. После успеха IsReady переключается в true через defer.
4. Настраивается Gin-движок (режим debug или release), подключается CORS, регистрируются роуты.
5. HTTP-сервер запускается в горутине.
6. При получении SIGINT или SIGTERM выполняется graceful shutdown с таймаутом 5 минут.

## Конфигурация

Конфигурация загружается через Viper с поддержкой нескольких источников в порядке приоритета: переменные окружения → файлы конфигурации (через флаг -config, поддерживаются YAML и .env через запятую) → дефолтные значения. Дефолты задаются в виде map и объединяются с дефолтами из пакетов логирования и подключения к БД через maps.Merge. Маппинг полей структуры конфига на ключи конфигурации осуществляется через теги mapstructure.

Структура Config включает секции:

- Логирование: уровень, вывод в файлы, директория, максимальный размер, количество резервных копий, возраст, сжатие.
- PostgreSQL: хост, пользователь, пароль, имя БД, порт, sslmode, часовой пояс.
- Приложение: режим работы (debug/release), порт HTTP-сервера, включение планировщика, ключ для криптоутилит, базовый URL сервиса.
- CORS: разрешённые origins через запятую.

Поле service_url автоматически корректируется: если оно равно http://localhost, к нему добавляется порт из app.port.

### Подключение к базе данных

Подключение к PostgreSQL осуществляется через синглтон GetPostgresConn с ленивой инициализацией (sync.Once). DSN включает lock_timeout=10s для предотвращения долгих блокировок. Настройки пула соединений: максимум 20 открытых, 10 простаивающих, без ограничения времени жизни. Логирование GORM заглушено (Silent режим).

## Миграции

Миграции реализованы через gormigrate. Список миграций формируется в internal/migrations/core.go и передаётся в Migrator. Применение происходит последовательно с автоматическим rollback при ошибке. После применения проверяется отсутствие «невалидных» миграций в БД — записей в таблице migrations, ID которых не соответствуют списку зарегистрированных миграций. Если такие найдены, приложение сообщает об ошибке и рекомендует пересоздать БД.

Поддерживается squash-миграция: специальная миграция для упаковки нескольких миграций в одну с последующим удалением записей о старых миграциях из БД. Таблица migrations расширяется полем applied_at для отслеживания времени применения.

## Дженерик-репозиторий и сервис

Пакет gorm_extra предоставляет типобезопасные абстракции для CRUD-операций: BaseRepository[T, ID] (интерфейс) и BaseRepositoryImpl[T, ID] (реализация), а также BaseService[T, ID] и BaseServiceImpl[T, ID]. Репозиторий работает через GORM и поддерживает как прямые вызовы (с получением соединения), так и операции в рамках транзакции (методы с суффиксом WithTx). Сервисный слой обёртывает репозиторий и добавляет транзакционную логику для пакетных операций (CreateMany, UpdateMany, DeleteMany).

## Пагинация и фильтрация

Пагинация реализована через morkid/paginate с расширенной поддержкой фильтрации. Структура PageParams содержит поля: номер страницы, размер, сортировка, карта фильтров и переключатель AND/OR логики между фильтрами. Для фильтрации строится JSON-фильтр в формате, понятном paginate, с экранированием спецсимволов.

Помимо стандартной сортировки, реализована релевантность: AddRelevanceOrders добавляет каскад ORDER BY с приоритетом совпадения — строгое начало слова → строгая середина → строгий конец → нестрогое начало → нестрогая середина → нестрогий конец → любое совпадение. Параметры пагинации валидируются: страница и размер должны быть положительными, поля сортировки проверяются against whitelist.

## Модели

Пакет gorm_extra предоставляет базовые модели:

- UuidId — UUID с авто-генерацией в BeforeCreate, если ID не задан.
- SerialId — целочисленный ID без autoIncrement, используется с GetAvailableId для поиска минимального свободного ID.
- StrId — строковый primary key.
- Timestamps — CreatedAt + UpdatedAt с timezone.

GetAvailableId учитывает занятые ID в рамках транзакции через context value usedIds, что позволяет корректно выделять последовательные ID при пакетном создании.

## Планировщик задач

Планировщик построен на gocron и хранит задачи в БД. Каждая задача описывается структурой Task с полями: ID, cron-расписание, флаг включения, описание и функция выполнения. При инициализации планировщик сверяет список зарегистрированных задач с БД: если задача не найдена — создаётся, если найдена — её параметры (расписание, включение) обновляются из БД. Задачи, которые есть в БД, но не зарегистрированы в коде, помечаются как выключенные и удаляются.

Две встроенные задачи:

- BackupTask (create_periodic_backup): еженедельное создание бэкапа БД (cron 0 0 * * 0). Использует блокировку через TaskLock для предотвращения параллельного выполнения, с тремя попытками при ошибке. На время выполнения сбрасывает IsReady. После успешного создания удаляет бэкапы старше одного года.
- UpdateTasks (update_tasks): каждые 5 минут синхронизирует параметры задач из БД с runtime-состоянием. При изменении параметров обновляет cron-job через UpdateTaskJob.

## Middleware

- IsReadyMiddleware: проверяет флаг IsReady; если приложение не готово, возвращает страницу «не готов» и прерывает запрос. Исключение — эндпоинт /api/v1/status/logs в debug-режиме.
- LogResponseMiddleware: логирует запросы с HTTP-статусом >= 400, включая тело запроса, query-параметры и путь.
- CORS: настраивается через gin-contrib/cors с разрешёнными origins из конфига.

## Роутинг

Роуты организованы иерархически: корневая группа → /api → /api/v1 → модульные группы (/status, /remotedb, /tasks). На корневой группе применяется IsReadyMiddleware. На уровне /api/v1 применяется LogResponseMiddleware. Корневой путь / отдаёт стартовую страницу. В debug-режиме подключается Scalar-документация на /api/scalar/docs.

Валидатор Gin настраивается для возврата имён полей из тегов json или form вместо имён полей структуры.

## Обработка ошибок

Пакет format_errors реализует кастомный тип TracedError, который автоматически захватывает файл и строку вызова Wrap через runtime.Caller. Функция FormatTree строит дерево ошибок с отступами и префиксами, показывая цепочку вызовов от верхнего уровня до корневой ошибки. Пути файлов сокращаются: отображается только часть от /internal/, /pkg/ или /cmd/.

В handler-слое используется methods.DuplicationError для различения ошибок дублирования ключа (SQLSTATE 23505) от других ошибок БД, возвращая соответствующие HTTP-статусы.

## Вспомогательные методы

Пакет internal/methods предоставляет хелперы для handler-слоя:

- BindAndValidate — биндинг тела запроса + опциональная валидация через интерфейс Validate().
- GetPageParams — извлечение и валидация параметров пагинации с проверкой полей сортировки.
- GetUuidFromPath и ValidateUuids — парсинг UUID из пути и массивов строк.
- GetExistedItems — проверка существования сущностей по списку ID с возвратом 404 для ненайденных.
- MapPage — маппинг страницы сущностей в страницу DTO через функцию-преобразователь.
- ValidationError — форматирование ошибок валидатора с указанием поля, условия и значения.

## Логирование

Логирование на базе zerolog с поддержкой двух режимов: только консоль или консоль + файл (через MultiWriter). Файловый лог использует lumberjack для ротации: настройка максимального размера файла, количества резервных копий, возраста и сжатия. Уровень лога настраивается в конфиге (по умолчанию trace). В debug-режиме доступен эндпоинт /api/v1/status/logs для скачивания логов.

Функция StreamLogs обходит директорию с логами и стримит содержимое всех файлов в HTTP-ответ с заголовками для скачивания.

## API-документация

Аннотации swaggo в handler-коде генерируют OpenAPI-спецификацию. В debug-режиме Scalar UI доступен на /api/scalar/docs. Спецификация отдаётся на /api/scalar/docs/openapi.json. В release-режиме Scalar отключён.

## Система бэкапов

Сервис BackupService обеспечивает создание, применение и удаление бэкапов БД. Создание бэкапа записывает метаданные (ID, время создания, размер, версия миграций) в таблицу public.backup. Применение бэкапа поддерживает стратегии восстановления: skip (пропустить конфликт), replace (заменить), fail (прекратить при конфликте). Эндпоинты для работы с бэкапами: получение списка с пагинацией, получение данных бэкапа, применение бэкапа, ручное создание бэкапа. Удаление старых бэкапов выполняется автоматически при создании нового (старше одного года).

## Graceful shutdown

При получении SIGINT или SIGTERM сервер выполняет graceful shutdown с таймаутом 5 минут. Это обеспечивает завершение активных запросов перед остановкой.

## Структура репозитория

### cmd/backend_go/

Точка входа приложения. Функция main инициализирует контейнер, запускает миграции в горутине, настраивает Gin-движок, регистрирует роуты, запускает HTTP-сервер и обрабатывает graceful shutdown по SIGINT/SIGTERM.

### internal/app_container/

DI-контейнер. Файл app_container.go определяет структуру Container и функцию GetContainer, которая последовательно инициализирует все слои. Файлы repositories_init.go, services_init.go, handlers_init.go, scheduler_init.go содержат методы инициализации соответствующих слоёв с передачей зависимостей.

### internal/config/

Конфигурация приложения. Структура Config с секциями для логирования, PostgreSQL, приложения и CORS. Функция GetConfig — синглтон с объединением дефолтов через maps.Merge. Содержит собственный README с описанием переменных окружения.

### internal/routes/

Регистрация HTTP-роутов. config.go — корневая инициализация: настройка валидатора, подключение IsReadyMiddleware, Scalar. api/config.go — инициализация группы /api. api/v1/config.go — инициализация группы /api/v1 с подключением LogResponseMiddleware и делегированием в модульные группы. Модульные группы (status, remotedb, tasks) — каждая содержит config.go с регистрацией конкретных эндпоинтов.

### internal/handlers/

HTTP-хендлеры. container.go — агрегирующая структура со ссылками на все хендлеры. Подпакеты по доменам: status (статус сервиса, версии миграций, бэкапы, логи), tasks (управление задачами планировщика), pages (стартовая страница, страница «не готов»). Каждый хендлер принимает зависимости через структуру Handler и реализует методы-обработчики Gin с swaggo-аннотациями.

### internal/services/

Бизнес-логика. container.go — агрегирующая структура со ссылками на все сервисы. Подпакеты: backup_services (создание, применение, удаление бэкапов), scheduled_services (логирование задач). Сервисы могут использовать как дженерик BaseServiceImpl, так и собственные реализации с дополнительной логикой и кастомными репозиториями.

### internal/repositories/

Слой доступа к данным. container.go — агрегирующая структура. Подпакеты: backup_repositories, scheduled_repositories. Репозитории расширяют BaseRepositoryImpl кастомными запросами и реализуют собственные интерфейсы.

### internal/models/

Доменные модели. base.go — общие модели и DTO (MessageResponse и др.). Подпакеты: public (модели в public-схеме, например Backup), scheduled_models (Task, TaskLog, TaskLock — в схеме scheduled).

### internal/migrations/

Список миграций. core.go — функция GetMigrationsList, возвращающая массив миграций gormigrate. Миграция «0» добавляет поле applied_at в таблицу migrations. Миграция «1» создаёт схему scheduled и таблицы задач, логов, блокировок и бэкапов.

### internal/middleware/

HTTP-middleware. container.go — структура с зависимостями (ссылки на контейнеры сервисов и хендлеров, флаг IsReady). is_ready_middleware.go — проверка готовности приложения. log_response_middleware.go — логирование ошибочных запросов с телом, query и путём.

### internal/scheduler/

Планировщик задач. scheduler_config.go — структура Scheduler и логика инициализации, проверки задач через БД, обновления cron-jobs в runtime. container.go — TasksContainer с описанием зарегистрированных задач. scheduler_tasks.go — задача UpdateTasks (синхронизация параметров из БД). backup_tasks.go — задача BackupTask (создание бэкапа с блокировкой, retry и очисткой старых бэкапов).

### internal/methods/

Вспомогательные функции для handler-слоя: биндинг и валидация, извлечение параметров пагинации, парсинг UUID, проверка существования сущностей, маппинг страниц DTO, обработка ошибок дублирования ключа и форматирование ошибок валидатора.

### internal/cors/

Настройка CORS через gin-contrib/cors с разрешёнными origins из конфига.

### internal/before_start/

Хуки для выполнения действий перед стартом сервера (после миграций). В шаблоне содержит закомментированный пример создания временного пользователя.

### pkg/config/

Универсальный загрузчик конфигурации на базе Viper. Поддержка флага -config для указания файлов (YAML и .env через запятую), переменных окружения, дефолтных значений и маппинга через mapstructure. Дженерик-функция Load[T] — синглтон с sync.Once.

### pkg/gorm_extra/

Утилиты для работы с GORM и PostgreSQL. Содержит: конфигурацию подключения и дефолты (Postgres struct, PostgresDefaults), синглтон-соединение (GetPostgresConn), дженерик-репозиторий и сервис с поддержкой транзакций (BaseRepository/BaseService), модели (UuidId, SerialId, StrId, Timestamps), пагинацию с фильтрацией и релевантностью (PageParams, Page, GetPageWithTx, AddRelevanceOrders), мигратор на базе gormigrate (Migrator, GetMigrator, ApplyMigrations), функцию GetAvailableId для поиска свободных ID в транзакциях.

### pkg/log/

Логирование на базе zerolog с ротацией через lumberjack. Поддержка консольного и файлового вывода через MultiWriter, настройка уровня, директории, размера и количества файлов. Функции GetLogger (синглтон) и StreamLogs (стриминг логов в HTTP-ответ).

### pkg/format_errors/

Кастомная обработка ошибок. Тип TracedError с захватом локации вызова (файл:строка через runtime.Caller), функция Wrap для обёртки ошибок с сообщением, FormatTree для построения дерева ошибок с отступами, shortenFilePath для сокращения путей до /internal/, /pkg/ или /cmd/.

### pkg/scalar/

Интеграция Scalar UI для отображения OpenAPI-документации. Обрабатывает Swagger JSON, gzip-скрипты и роуты для Scalar. Подключается только в debug-режиме.

### pkg/utils/

Утилиты общего назначения. utils.go — общие хелперы. crypt.go — криптоутилиты (используют ключ из конфига). maps/maps.go — утилиты для работы с map: Merge (слияние нескольких map в одну) и FromHash (преобразование массива сущностей в map по ID).

### pkg/http_tcp_connector/

Серверная часть интеграции с tcp_http_bridge — отдельным клиентским инструментом (https://github.com/Haonixao/tcp_http_bridge), который позволяет получить доступ к закрытому ресурсу (например, базе данных) через приложение как прокси. Клиент tcp_http_bridge запускается локально у разработчика, слушает TCP-порт и перенаправляет трафик через HTTP-запросы к этому пакету. Пакет, в свою очередь, устанавливает реальное TCP-соединение к целевому ресурсу (по умолчанию — localhost:5432, адрес PostgreSQL из конфига) и транслирует данные в обе стороны.

Принцип работы: каждая TCP-сессия клиента получает уникальный ID. Данные от клиента передаются через POST /send_data, ответные данные от БД забираются через long-polling в POST /get_data (таймаут 30 секунд, после чего возвращается 204 No Content). При первом обращении автоматически создаётся сессия с TCP-соединением к целевому ресурсу. Сессии имеют буфер на 1000 пакетов для ответов от БД, таймаут неактивности 5 минут и cleanup закрытых сессий через 10 минут. Эндпоинт GET /get_meta отдаёт метаданные подключения (user, password, db), которые настраиваются при инициализации роутов.

Роуты remotedb регистрируются только в debug-режиме (internal/routes/api/v1/remotedb/config.go). Поскольку эндпоинты являются обычными Gin-хендлерами, на них можно накладывать ту же аутентификацию и middleware, что и на любые другие защищённые роуты приложения.

Пакет также предоставляет версии хендлеров для net/http (HandleSendDataHTTP, HandleGetDataHTTP, HandleGetMetaHTTP) для использования вне Gin.
